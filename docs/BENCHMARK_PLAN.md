# MongoDB vs PostgreSQL — план сравнения для доклада (Java-сообщество)

Документ фиксирует архитектуру, стек, сценарии сравнения, метрики и порядок выполнения.  
Цель: материал доклада с честными замерами под **одинаковой** конкурентной нагрузкой (p95/p99, процессор, память).

---

## 1. Цель и тезис доклада

**Практический вопрос:** как ведут себя **нормализованный Postgres**, **Mongo с тегами внутри документа**, **Mongo с `$lookup`** и **Postgres JSONB** на одних и тех же объёмах и числе потоков — у кого ниже задержки и расход ресурсов, как растёт деградация при росте данных и параллелизма.

**Что показываем аудитории:**

1. Нормализованный Postgres (товар + теги 1:N) против Mongo с тегами внутри документа.
2. Postgres JSONB (**весь продукт в поле `doc`**) против документа Mongo при поиске по вложению — проверка тезиса «у Postgres JSON даже быстрее».
3. Mongo: товар целиком в документе, **`$lookup` только за тегами** — против соединения товар↔теги в Postgres.
4. Не только задержка чтения, но изменение и удаление, агрегации, **диск**, **время построения индексов**, **процессор и память**.
5. Выводы — по таблицам и графикам p95/p99 и ресурсов при **одинаковых** «объём × число потоков».

## 2. Железо и ограничения прогона

| Ресурс | Значение |
|--------|----------|
| Процессор | Intel i5-9400F, 6 ядер / 6 потоков |
| Память | 32 GB |
| Диск | NVMe ~900 GB (~800 GB свободно) |

**Лестница объёмов (товаров):** `10K → 100K → 1M → 5M`.

**Где крутим:** приложения на хосте, базы и Prometheus — в Docker Compose.

**Раздельный запуск:** вызовы наполнения и замера для Postgres и Mongo идут **по очереди**.  
Порядок на каждой ступени объёма: сначала полностью Postgres (наполнение → все нужные замеры), затем полностью Mongo (наполнение → замеры).

### Потоки нагрузки и соединения с БД

Две разные вещи:

| Что | Роль |
|-----|------|
| **Потоки генератора нагрузки** | сколько запросов выполняется одновременно |
| **Пул соединений** (Hikari / Mongo) | сколько одновременных сессий к БД может держать приложение |

**Правило для честного замера:**  
размер пула ≥ числа потоков нагрузки на каждом прогоне.  
Иначе p95 раздувается ожиданием свободного соединения, а не работой Postgres/Mongo.

#### Фиксированные числа (для этой машины: 6 ядер / 32 GB)

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Потоки нагрузки | **1 → 8 → 16 → 32** | основная лестница; 6 ядер, без лишнего шума планировщика |
| Hikari `maximumPoolSize` | **32** | равен максимуму лестницы потоков |
| Пул соединений Mongo `maxSize` | **32** | симметрично Hikari |
| Postgres `max_connections` | **100** | запас: 32 под приложение + суперпользователь, мониторинг, ручные сессии |
| Mongo `maxIncomingConnections` | по умолчанию | не ниже пула приложения |

**Пул = 32** на всех прогонах. Меняются объём данных в БД и число потоков нагрузки.

**Наполнение:** отдельный этап (см. §8) — пакетная вставка из файла.  
Его **тоже замеряем** (время заливки, время индексов, диск, CPU/RAM), но в **отдельной** таблице отчёта — не смешиваем с p95 операций `FIND`/`UPDATE`/`DELETE`.

## 5. Модель данных и кейсы

Предметная область: **товар + теги** (смысл 1:N).

### Кейс A — нормализация (Postgres) против вложенных тегов (Mongo)

**Зачем:** классический спор «соединение таблиц против документа с массивом».

**Postgres (нормализованно):**

```sql
product (
  id          BIGINT PRIMARY KEY,
  name        TEXT NOT NULL,
  price       NUMERIC(12,2) NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL
);

product_tag (
  product_id  BIGINT NOT NULL REFERENCES product(id),
  tag         TEXT NOT NULL,
  PRIMARY KEY (product_id, tag)
);

CREATE INDEX idx_product_tag_tag ON product_tag(tag);
```

**Mongo (теги внутри документа):**

```js
{
  _id: NumberLong(...),
  name: "...",
  price: ...,
  createdAt: ISODate(...),
  tags: ["tag1", "tag2", ...]
}
// индекс по массиву: { tags: 1 }
```

### Кейс B — весь продукт как JSON (Postgres JSONB против документа Mongo)

**Зачем:** одинаковая модель «документ целиком»; проверка тезиса «у Postgres JSON даже быстрее». **Весь продукт** лежит в JSON.

**Postgres (одна строка = один JSONB-документ):**

```sql
product_doc (
  id   BIGINT PRIMARY KEY,           -- дублирует doc->>'id' для удобного первичного ключа
  doc  JSONB NOT NULL
);

-- весь продукт внутри doc, например:
-- {
--   "id": 1,
--   "name": "...",
--   "price": 19.99,
--   "createdAt": "2026-01-01T00:00:00Z",
--   "tags": ["a", "b"]
-- }

CREATE INDEX idx_product_doc_tags_gin
  ON product_doc USING GIN (doc jsonb_path_ops);
-- поиск по тегу: doc @> '{"tags":["wanted"]}'::jsonb
```

Чтение и изменение в кейсе B идут через `doc` (`jsonb_set` / `||` для тегов), а не через отдельные колонки `name`/`price`.

**Mongo:** тот же полный документ, что в кейсе A — одна коллекция, все поля и `tags` внутри.

### Кейс C — Mongo: товар целиком в объекте, `$lookup` только за тегами

**Зачем:** поля товара лежат в документе, **только теги** вынесены в отдельную коллекцию и подтягиваются через `$lookup`. Сравниваем с соединением `product` ⋈ `product_tag` в Postgres (кейс A, метка `pg-norm`).

**Mongo:**

```js
// коллекция tags — справочник тегов
{ _id: NumberLong(...), name: "electronics" }
// индекс: { name: 1 }

// коллекция products — сам товар целиком в объекте
{
  _id: NumberLong(...),
  name: "...",
  price: ...,
  createdAt: ISODate(...),
  // ... любые другие поля товара тоже здесь, не через lookup
  tagIds: [ NumberLong(...), ... ]   // единственные ссылки наружу — на tags
}
// индекс: { tagIds: 1 }
```

**Правило:** `$lookup` используется **только** для коллекции `tags`. Имя, цена, даты и прочие атрибуты товара из других коллекций не джойним.

Вариант конвейера (зафиксировать один и не менять между прогонами):

```js
db.products.aggregate([
  { $match: { tagIds: <tagId> } },
  { $limit: 50 },
  { $lookup: {
      from: "tags",
      localField: "tagIds",
      foreignField: "_id",
      as: "tags"
  }}
])
```

После `$lookup` в ответе: все поля товара как были + массив `tags` с документами тегов.

**Postgres (сравнение):** те же запросы, что в кейсе A (`product` ⋈ `product_tag`) — метка `pg-norm`.  
**Метка Mongo:** `mongo-lookup`. Метка `mongo` — строки тегов в массиве `tags` внутри документа (кейс A/B).

**Важно для честности:** кейс C берёт те же товары и теги из тех же файлов, что A/B; отличается только раскладка (строки тегов в справочнике + `tagIds`, а не массив строк в документе).

### Загрузка данных (наполнение) — как именно

Наполнение — **отдельный этап до замеров**. Postgres и Mongo наполняем **по очереди** (ресурсы), а **один и тот же набор** берём из общего файла.

#### Теги: много и разные, но совпадающие

| Параметр | Значение |
|----------|----------|
| Размер словаря тегов `T` | **50 000–100 000** уникальных |
| Тегов на товар | 3–15, с перекосом: часть тегов «горячие», часть редкие |
| Имена тегов | разные строки; у товаров разные наборы привязок |

Справочник тегов и привязки к товарам совпадают между Postgres и Mongo — не только поля товара.

#### Файл как источник истины

Грузим из файла — так проще гарантировать, что наборы не разъедутся.

```
1) Скрипт generate-dataset → tags.jsonl + products.jsonl на диске
2) Приложение загружает те же файлы в Postgres
3) Приложение загружает те же файлы в Mongo
```

Формат:

- `tags.jsonl` — словарь `{ "id": 1, "name": "electronics-pro-0042" }` (id в файле для lookup);
- `products.jsonl` — `{ ..., "tags": ["electronics-pro-0042", ...] }` — **теги всегда текстовые**.

При заливке в БД:

- **PG_NORM / PG_JSON / MONGO** — теги остаются текстом (без id);
- **MONGO_LOOKUP** — текст → `tagIds` по словарю (id появляются только здесь).

**Генерация файлов — скрипт** (не сервис приложения), например:

```bash
./scripts/generate-dataset.sh \
  --volume 100000 \
  --tag-count 100000 \
  --generator 42 \
  --out-dir data/v100k
```

Реализация: Java CLI (`GenerateDatasetMain` в модуле `common`), запуск через `./scripts/generate-dataset.sh` / `./gradlew :common:run`.

**Заливка в БД — приложение** (или кнопка **Load** в Bench UI):

```
POST /api/data/load
{
  "dataDir": "/abs/path/to/data/v100k",
  "storageCase": "PG_NORM",
  "rebuildIndexes": true,
  "clearBeforeLoad": true
}
```

`storageCase`: `PG_NORM` / `PG_JSON` на `:8081`; `MONGO` / `MONGO_LOOKUP` на `:8082`.  
`dataDir` — **абсолютный** путь к каталогу с `tags.jsonl` и `products.jsonl`.  
При загрузке: embed/json/norm берут текст как есть; lookup мапит текст → id.

**Дозаливка объёма:** скрипт дописывает в файл только новые `id`, затем `load` догружает хвост в обе СУБД из того же каталога/дополнения.

#### Будет ли файл медленным?

На NVMe **узкое место — запись в БД и индексы**, не чтение файла.

| Этап | Оценка |
|------|--------|
| Чтение JSONL с NVMe | обычно малая доля времени заливки |
| `INSERT` / `bulkWrite` + индексы | основная стоимость |

Ориентир: 1M товаров ≈ **0.5–2 GB** JSONL — нормально. Читать потоком, вставлять пакетами 1000–5000.

#### Алгоритм заливки в СУБД (сначала Postgres, потом Mongo)

1. Очистить таблицы/коллекции выбранных кейсов.
2. Загрузить `tags.jsonl` → справочник.
3. Читать `products.jsonl` пакетами → писать в нужный кейс:
   - **A (PG):** `product` + `product_tag`;
   - **B (PG):** `product_doc` с полным JSONB `doc`;
   - **A/B (Mongo):** документы с массивом строк `tags`;
   - **C (Mongo):** `products` с полями товара + `tagIds`.
4. Создать индексы, замерить время построения.
5. `ANALYZE` (Postgres) / аналог статистики.
6. Сверка Postgres ↔ Mongo: count, выборка одних и тех же `id`.

**Что снимаем на этапе заливки** (на каждом целевом объёме / дозаливке, по варианту хранения):

| Метрика | Смысл |
|---------|--------|
| Время чтения файла + вставки | wall-clock от старта `load` до конца пакетов |
| Время построения индексов | отдельно, после (или до — как зафиксируем) вставки |
| Размер данных / индексов на диске | после заливки |
| CPU / RAM приложения и контейнера БД | среднее и max за окно заливки |

Это материал для слайда «диск и индексы», не для таблицы p95 поиска.

## 6. Операции сравнения (единый контракт)

| Операция | Смысл | Семантика |
|----------|--------|-----------|
| `FIND_BY_TAG` | страница товаров с тегом | размер страницы 50; A: соединение / вложенные теги; B: полный jsonb / документ Mongo; C: `$lookup` / соединение |
| `FIND_BY_ID` | точечное чтение | опора для сравнения; в B — по `id` / `_id`, тело из `doc` |
| `UPDATE_TAG` | добавить тег товару (если нет) | PG-norm: INSERT; B: `jsonb_set` по тегам в `doc`; mongo: изменить массив строк; lookup: `$addToSet` в `tagIds` (поля товара не трогаем) |
| `DELETE_BY_TAG` | убрать тег у товара | симметрично изменению |
| `AGG_COUNT_BY_TAG` | число товаров с тегом | одинаковый результат |
| `AGG_TOP_TAGS` | top-N тегов по частоте | PG: `GROUP BY`; вложенные теги: `$unwind`; lookup: по `tagIds` / справочнику `tags` |

**Агрегации на честных условиях:**

- один и тот же результатный набор;
- одинаковый набор полей в выборке / проекции;
- отдельно помечать **холодный** и **прогретый** кэш страниц ОС/БД;
- индексы на месте у обоих вариантов.

## 7. Метрики и критерии оценки

### 7.1. Как сравниваем

Фиксируем **одинаковую нагрузку** на все варианты: тот же объём, число потоков, операция, прогрев/измерение, размер страницы.  
Смотрим, **на каком уровне** держатся задержки и ресурсы.

Интересует:

- абсолютные p50 / p95 / p99 и операций в секунду на каждой ступени лестницы;
- как растут p95/p99 при увеличении объёма и потоков (форма деградации);
- отношение p95 между вариантами на одной ступени (например `pg-norm / mongo`);
- процессор и память приложения и БД при том же числе потоков.

Повторы: 3 прогона, в отчёт — медиана. В выводах опираемся на p95/p99.

### 7.2. Что снимаем

| Категория | Метрики | Как снимаем |
|-----------|---------|-------------|
| Задержка | p50, p95, p99, max | JSON `/api/bench/run` + Prometheus `bench_p50_ms` / `bench_p95_ms` / `bench_p99_ms` |
| Пропускная способность | операций/с | JSON + `bench_ops_per_second` |
| Ошибки | число ошибок за окно | JSON + `bench_errors` |
| **Процессор** | % CPU приложения и контейнера БД | Prometheus `process_cpu_usage` + `docker stats` |
| **Память** | heap JVM; RSS контейнера БД | Prometheus `jvm_memory_used_bytes` + `docker stats` |
| Пул соединений | active / pending / timeout | Prometheus `hikaricp_*` / Mongo pool |
| Диск | данные и индексы отдельно | JSON `/api/data/load` + `bench_data_bytes` / `bench_index_bytes` |
| Индексы | время построения | JSON + `bench_index_build_ms` |

Источник перцентилей — HdrHistogram в `LoadRunner`; `BenchMetricsExporter` публикует итог в Micrometer Gauge  
с метками `storage_case`, `operation`, `concurrency`, `volume` (накопление по лестнице прогонов до рестарта JVM).

Процессор и память — колонки отчёта на каждый прогон.

**Метки метрик:** кейс (`A`/`B`/`C`), вариант хранения (`pg-norm` / `pg-json` / `mongo` / `mongo-lookup`), операция, объём, число потоков.

### 7.3. Что выносим на слайды

1. Таблицы и графики p95/p99 при одинаковых «объём × потоки» (кейс A: `pg-norm` против `mongo`).
2. Отношения p95: `pg-norm / mongo`, `pg-json / mongo`, `mongo-lookup / pg-norm` по лестнице.
3. Диск: ГБ на 1M документов + накладные расходы индексов.
4. Время построения индексов (секунды).
5. Агрегации: p95 при прогретом кэше.
6. **Процессор и память:** кто сколько ест при одинаковом числе потоков.

## 8. Этапы дня: объём → потоки → что меняется

### 8.0. Две фазы

| Фаза | Что делаем | Меняется | Фиксировано |
|------|------------|----------|-------------|
| **НАПОЛНЕНИЕ** | Кладём товары в БД | объём (10K → 100K → …) | пул = 32 |
| **ЗАМЕР** | Гоняем операции под нагрузкой | число потоков (1→8→16→32), операция, кейс | пул = 32, данные уже лежат |

Лестницы две — **объём данных** и **число потоков нагрузки**. Пул соединений = 32.

```
для каждого объёма в [10K, 100K, 1M, 5M]:
    --- блок Postgres ---
    1) НАПОЛНЕНИЕ Postgres до этого объёма
    2) снять размер на диске / проверить индексы
    3) для каждого кейса Postgres (A: pg-norm, B: pg-json, …):
         для каждого числа потоков в [1, 8, 16, 32]:
              для каждой операции:
                   прогрев → измерение → записать p95/p99, CPU, RAM

    --- блок Mongo ---
    4) НАПОЛНЕНИЕ Mongo до этого объёма
    5) снять размер на диске / проверить индексы
    6) для каждого кейса Mongo (mongo, mongo-lookup, …):
         для каждого числа потоков в [1, 8, 16, 32]:
              для каждой операции:
                   прогрев → измерение → записать p95/p99, CPU, RAM
```

Вызовы API (`/api/data/load`, `/api/bench/run`) — через curl или Bench UI (`http://localhost:8081/` / `:8082/`) — к Postgres и Mongo идут **по очереди**.

### 8.1. Пример «на пальцах» — один объём 100K, кейс A

1. **Наполнить Postgres** до 100K (кейсы A+B) → все замеры Postgres на 100K.
2. **Наполнить Mongo** до 100K (вложенные теги + `$lookup`) → все замеры Mongo на 100K.
3. В блоке Postgres для `FIND_BY_TAG` / `pg-norm`:
   - прогон с 1 потоком → строка в results;
   - 8 потоков → строка;
   - 16 потоков → строка;
   - 32 потока → строка.
4. Остальные операции Postgres, затем блок Mongo для `mongo` / `mongo-lookup`.
5. Кейсы B/C на **тех же 100K** используют уже залитые данные.
6. Дальше — **доливка до 1M**: снова блок Postgres, затем блок Mongo.

Итого на одном объёме для одной операции и двух вариантов хранения: **8 строк** (2 варианта × 4 значения потоков).  
При смене числа потоков данные те же.

### 8.2. Что чувствует БД на каждом шаге

| Шаг | В БД лежит | Одновременно запросов | Занято соединений из пула (примерно) |
|-----|------------|------------------------|--------------------------------------|
| Наполнение 100K | растёт до 100K | пакетная вставка | несколько (загрузка) |
| Замер, 1 поток | 100K | 1 | ≤ 1 |
| Замер, 8 потоков | 100K | 8 | ≤ 8 |
| Замер, 16 потоков | 100K | 16 | ≤ 16 |
| Замер, 32 потока | 100K | 32 | ≤ 32 (= весь пул) |
| Наполнение → 1M | растёт до 1M | пакет | несколько |
| Замер снова | 1M | 1…32 | ≤ числа потоков |

Смысл: при 1 потоке смотрим «одиночную» задержку; при 32 — как держится под полной шириной пула на том же объёме.

### 8.3. Параметры одного прогона замера

| Параметр | Значение |
|----------|----------|
| Прогрев | 10–30 с |
| Измерение | ≥ 60 с |
| Размер страницы | 50 |
| Повторы | 3, в отчёт — медиана |
| Режим | прогретый кэш (по умолчанию); холодный — отдельной пометкой |
| Вместе с задержкой | % CPU и память приложения + БД |
| Пул | всегда 32 |

Один прогон = одна строка: *кейс + вариант хранения + объём + операция + число потоков*.

Пример: «A, pg-norm, 100K, FIND_BY_TAG, 16 потоков» → p95/p99, операций/с, CPU, RAM.

## 8a. Чеклист замеров (что прогнать для доклада)

**Шаг 0 — проверка стенда:**

- наполнить 10K → замер `FIND_BY_TAG` при 1 и 8 потоках: сначала Postgres, потом Mongo;
- индексы работают, метрики и CPU/RAM пишутся.

**Кейс A (соединение Postgres против вложенных тегов Mongo)** — основной сюжет:

| Что меняем | Какие значения |
|------------|----------------|
| Варианты | `pg-norm`, `mongo` |
| Объёмы | 10K, 100K, 1M, 5M |
| Операции | `FIND_BY_TAG`, `UPDATE_TAG`, `DELETE_BY_TAG` |
| Потоки | **1, 8, 16, 32** |
| Пул | **32** (фиксирован) |

На каждом объёме: сначала наполнение (или дозаливка), потом все значения потоков.

**Кейс B (весь продукт в JSONB против документа Mongo):**

| Варианты | `pg-json`, `mongo` |
|----------|---------------------|
| Потоки / пул | 1, 8, 16, 32 / пул 32 |

Данные кейса B появляются при том же наполнении, что и A (в Postgres — таблица `product_doc`).

**Кейс C (`$lookup` против соединения):**

| Варианты | `mongo-lookup`, `pg-norm` |
|----------|---------------------------|
| Объёмы | 10K, 100K, 1M |
| Операции | в первую очередь `FIND_BY_TAG` |
| Потоки / пул | 1, 8, 16, 32 / пул 32 |

**Агрегации (прогретый кэш):** объёмы 100K и 1M; операции `AGG_*`; потоки 1, 8, 16.

**Диск и построение индексов:** один раз на максимальном объёме дня для каждого варианта хранения.

### Сокращённый день

```
НАПОЛНЕНИЕ + ЗАМЕР блок Postgres @ 100K
НАПОЛНЕНИЕ + ЗАМЕР блок Mongo @ 100K
НАПОЛНЕНИЕ + ЗАМЕР блок Postgres @ 1M
НАПОЛНЕНИЕ + ЗАМЕР блок Mongo @ 1M
снять размер диска + время индексов (по одной СУБД)
```

Внутри блока Postgres: кейсы A/B (и pg-norm для C).  
Внутри блока Mongo: `mongo`, `mongo-lookup`.  
Числа потоков: 8 и 32; операции: поиск (+ изменение для A).

## 9. Правила честности

1. Датасет = общие файлы `tags.jsonl` + `products.jsonl`; обе СУБД грузятся из них. Словарь тегов большой (десятки–сотни тысяч), привязки разнообразные.
2. После заливки — сверка Postgres ↔ Mongo (count + выборка по `id`).
3. Одинаковый размер страницы / limit / top-N.
4. Индексы созданы и используются (проверить планом запроса); в кейсе C — индексы на `tagIds` и `tags.name`.
5. Режим кэша (холодный / прогретый) помечать; сравнивать прогоны в одном режиме.
6. Версии PostgreSQL 17 / MongoDB / Spring Boot 4 / Java 25 и параметры Compose — на слайд «методика».
7. Параметры обеих СУБД настраивать симметрично.
8. Наполнение и замер Postgres и Mongo — **по очереди**.
9. Кейс C: `$lookup` **только** на `tags`.
10. Горячий путь на JDBC/native при необходимости — с пометкой в методике.

## 12. Осознанно вне скоупа

- Grafana / дашборды (достаточно Bench UI, UI Prometheus и таблиц в `results`).
- Внешние генераторы нагрузки (JMeter, Gatling) — нагрузка внутри приложения.
- Кластер, реплики, шардирование.
- Объёмы 10M+ / «сотни миллионов» в одном дневном прогоне.
- Отдельный кейс «ORM против сырого SQL».
- Заранее заданные пороги задержки («прошёл / не прошёл», «≤ N мс»).
- Сравнение холодного прогона одной СУБД с прогретым другой.
- Одновременная нагрузка на Postgres и Mongo.
- Число потоков нагрузки больше размера пула соединений.
- В кейсе C — `$lookup` не только на теги / джойн прочих сущностей.
- Агрегации Mongo без индексов против SQL с индексами (и наоборот).
